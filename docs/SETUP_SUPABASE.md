## 0. Почему команды пишутся с `.cmd`

В PowerShell по умолчанию запрещено выполнение сценариев, а `npm` и `npx` —
это `.ps1`-обёртки. Отсюда ошибка «выполнение сценариев отключено в этой
системе». Рядом лежат `npm.cmd` и `npx.cmd`, которые запрет не затрагивает,
поэтому дальше везде они.

Менять политику безопасности Windows ради этого не нужно. Если всё же хочется
писать команды без `.cmd`, это ваше решение и делается один раз:
`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

## 1. Связать репозиторий с проектом

```bash
npx.cmd supabase login
```

Команда откроет браузер — войдите сами, я в чужие аккаунты не вхожу.

Дальше нужен **ref dev-проекта**: это часть адреса
`https://<ref>.supabase.co` со страницы `Project Settings` → `General`.

```bash
npx.cmd supabase link --project-ref ВАШ_REF_DEV
```

Спросит пароль базы — тот, что вы задавали при создании проекта. Он остаётся у
вас, мне не нужен.

## 2. Накатить схему

```bash
npm.cmd run db:push
```

Команда покажет список из пяти миграций и спросит подтверждение. Если что-то
упадёт — пришлите текст ошибки целиком, я поправлю миграцию. Руками SQL не
правьте: боевой проект должен получить ровно ту же схему.

**Если CLI по какой-то причине не свяжется**, всё то же самое можно сделать
через `SQL Editor` в панели: выполнить пять файлов из `supabase/migrations/`
**строго по порядку имён**, каждый целиком.

## 3. Проверить политики

Откройте `SQL Editor` → `New query`, вставьте целиком
`supabase/tests/rls_check.sql`, выполните.

Скрипт создаёт двух временных пользователей, проверяет два десятка границ
доступа и удаляет их за собой. В ответе будет таблица — столбец «результат»
должен быть `ok` во всех строках.

Что он проверяет: чужая библиотека невидима, дружба сама по себе её не
открывает, друг не правит чужой фильм, оценку нельзя поставить от чужого
имени, браузер не пишет в журнал колеса, перенос библиотеки игнорирует чужой
`owner_id` из данных и отказывается работать дважды.

Любой `ПРОВАЛ` — дефект в политиках, а не в скрипте. Пришлите строку.

## 4. Создать первое приглашение

Регистрация закрытая, поэтому первый код заводится вручную — в том же
редакторе:

```sql
insert into public.invites (code) values ('CINEVLT1');
```

Дальше каждый пользователь создаёт до пяти приглашений сам.

## 5. Отдать мне два публичных значения

`Project Settings` → `API`. Пришлите сюда `Project URL` и ключ `anon public` —
я впишу их в [src/config.js](../src/config.js) и проверю вход. Оба значения
публичные: анонимный ключ и так уедет в браузер каждому пользователю, доступ
ограничивают политики.

Ключ `service_role` с той же страницы **не присылайте** — он обходит все
политики. Если он понадобится скриптам, вы положите его в `.env.local` сами.

Не хотите пересылать — впишите сами:

```js
export const SUPABASE_URL = "https://<ваш-ref>.supabase.co";
export const SUPABASE_ANON_KEY = "<anon public>";
```

## 6. Упростить себе жизнь на время разработки

В dev-проекте: `Authentication` → `Sign In / Providers` → `Email` → выключите
`Confirm email`. Тогда регистрация сразу даёт сессию и не придётся ждать письма
от встроенного отправителя Supabase с его жёстким лимитом.

**На боевом проекте подтверждение почты обязательно** — вместе со своим доменом
и SMTP-отправителем, иначе сотня писем не дойдёт.

## 7. Пройти сценарий целиком

```bash
npm.cmd start
```

Откройте `http://localhost:8765/`. Шлюз входа включится сам, как только в
`config.js` появятся ключи. Порядок: регистрация с кодом `CINEVLT1` → вход →
библиотека.

Библиотека читается из аккаунта: локального хранилища записей больше нет.
После первого входа она пуста — это нормально, наполняется она через
«Добавить фильм» и поиск в TMDB.

## 8. Проверить хранилище библиотеки

```bash
npm.cmd run check:library
```

Скрипт заводит двух временных пользователей, наполняет библиотеку одним
пакетом, читает её обратно и проверяет связи, транзакцию, ревизию и то, что
чужие строки не видны. За собой он убирает. Рядом стоят `npm run check:rls`
и `npm run check:functions`.
