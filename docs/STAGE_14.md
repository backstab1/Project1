Схема, политики доступа и проверка находятся в репозитории. Чтобы их
применить, нужен проект Supabase — его создаёте вы, потому что аккаунты и
платежи я не завожу и ваши пароли не ввожу.

## Шаги

### 1. Node.js

Установите Node.js LTS с [nodejs.org](https://nodejs.org). Сейчас его на машине
нет: `npm test` никогда не запускался, проверялась только python-часть.

После установки, в новом окне терминала:

```bash
node --version && npm install && npm test
```

Двадцать с лишним наборов тестов предметной области должны пройти до того, как
мы начнём что-то менять — дальше они наша страховка.

### 2. Проекты Supabase

Заведите аккаунт на [supabase.com](https://supabase.com) и создайте **два**
проекта: `cinevault-dev` и `cinevault-prod`. Регион — ближайший к вам.
Оба на бесплатном тарифе; `cinevault-prod` переведём на платный в этапе 16,
до переноса настоящей библиотеки.

Пароль базы данных сохраните в менеджере паролей. Мне он не нужен.

### 3. Ключи

В настройках dev-проекта (`Project Settings → API`) возьмите адрес проекта,
анонимный ключ и ключ `service_role`. Скопируйте `.env.example` в `.env.local`
и заполните. Файл в Git не попадёт.

Анонимный ключ публичный — он попадёт в `src/config.js` и будет виден всем, это
нормально: доступ ограничивают политики. Ключ `service_role` не показывайте
никому, включая меня в переписке.

### 4. Применение миграций

```bash
npx supabase login
```

Команда откроет браузер — войдите сами. Затем свяжите репозиторий с
dev-проектом и накатите миграции:

```bash
npx supabase link --project-ref <ref-dev-проекта>
```

```bash
npm run db:push
```

### 5. Первое приглашение

Регистрация закрытая: аккаунт без профиля не видит ничего, а профиль выдаётся
в обмен на код. Самый первый код создаётся вручную — в `SQL Editor`
dev-проекта:

```sql
insert into public.invites (code) values ('CINEVLT1');
```

Дальше каждый пользователь может создать до пяти приглашений сам.

### 6. Проверка политик

```bash
npm run check:rls
```

Скрипт создаёт двух временных пользователей, проверяет два десятка границ —
чужая библиотека невидима, дружба сама по себе её не открывает, оценку нельзя
поставить от чужого имени, браузер не пишет в журнал колеса — и удаляет
пользователей за собой. На боевом проекте он не запускается.

Все проверки должны быть зелёными. Это и есть критерий готовности этапа 14.

## Что делать после

Этап 15 — авторизация. Он упирается в две вещи, которые тоже за вами: домен и
почтовый отправитель. Без своего домена письма подтверждения уходят в спам, а
встроенной почты Supabase на сотню человек не хватит по лимитам. Пока домена
нет, dev-проект живёт на встроенной почте — этого достаточно, чтобы собрать и
проверить экраны входа.
