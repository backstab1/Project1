# Решения и открытые вопросы

## Зафиксированные решения

- ~~приложение личное, обычно используется двумя зрителями~~ — пересмотрено;
- платформа — Windows, минимальное разрешение 1366×768;
- интерфейс только на русском языке;
- ~~обязательная работа без интернета~~ — пересмотрено;
- объём библиотеки — до 500 фильмов;
- архитектуру исходного прототипа разрешено полностью заменить;
- фильм находится только в одном пользовательском списке;
- списки поддерживают иерархию;
- порядок списков и фильмов задаётся вручную;
- удаление списка переносит фильмы в «Без списка»;
- фильм входит максимум в одну франшизу;
- франшиза не содержит другие франшизы;
- победа франшизы отмечает просмотренными все входящие фильмы;
- повторные просмотры не хранятся;
- оценка имеет шаг 0,5;
- один зритель имеет одну оценку на фильм; зритель определяется аккаунтом,
  а не написанием имени;
- новая оценка зрителя заменяет предыдущую;
- незавершённая сессия не сохраняется;
- завершённые сессии сохраняются;
- шансы всех участников равны;
- сейвы принадлежат игрокам и расходуются только внутри сессии;
- приложение использует золотой стиль CineVault;
- пробел запускает вращение колеса;
- ~~основной слой хранения новой версии — IndexedDB~~ — пересмотрено;

## Пересмотренные решения: переход на серверную версию

Приняты 24 августа 2026 года, действуют начиная с этапа 14. План перехода —
[SERVER_MULTIUSER_PLAN.md](SERVER_MULTIUSER_PLAN.md).

- приложение многопользовательское, данные принадлежат аккаунту;
- ожидаемая аудитория — до 100 пользователей;
- TMDB-токен один на весь сервис и хранится как секрет Edge Function;
  расход ограничен дневной квотой на аккаунт, счётчик — в `tmdb_usage`;
- постеры отдаются с CDN TMDB, собственный кэш изображений не ведётся;
- бэкенд — Supabase: Postgres, Auth, Realtime, Storage, Edge Functions;
- работа без интернета не требуется: клиент тонкий, источник правды — сервер,
  IndexedDB остаётся кэшем последнего снимка;
- вход по email и паролю; гостевого режима без аккаунта нет;
- взаимодействие между пользователями идёт только через принятую заявку в
  друзья;
- друзьям доступны: совместная сессия колеса в реальном времени, чтение
  библиотеки друга, общие списки и коллекции, взаимные оценки;
- библиотека по умолчанию скрыта: видимость для друзей включается вручную;
- разграничение доступа обеспечивается политиками Row Level Security, а не
  проверками в клиенте; клиент работает только с анонимным ключом;
- случайность колеса и право хода определяет сервер, клиент только
  отрисовывает результат;
- незавершённая сессия сохраняется на сервере (отменяет решение
  «незавершённая сессия не сохраняется» начиная с этапа 20);
- правила предметной области остаются одним экземпляром кода в `src/domain/*`
  и используются и браузером, и Edge Functions;
- библиотека хранится только в аккаунте: файловых выгрузок и загрузок в
  приложении нет — ни резервной копии JSON, ни выгрузки CSV, ни импорта
  таблиц, ни переноса старой локальной базы. Сохранность данных обеспечивают
  резервные копии базы на стороне сервиса (решение 27 августа 2026 года,
  отменяет весь этап 8 «Импорт и резервные копии»);
- IndexedDB остаётся только снимком последней загрузки — на чтение, ради
  мгновенного старта и экрана при обрыве связи;
- одновременную правку разрешает ревизия библиотеки, а не время изменения
  строки: приложение пишет пакетами, собранными из снимка всей библиотеки,
  и построчная проверка их не защищает;
- имя зрителя не вводится руками: зритель — это аккаунт, свой или друга.
  Оценка хранит идентификатор аккаунта, а имя рядом — снимок на момент
  оценки, чтобы смена имени в профиле не переписывала историю (отменяет
  решение «сохранение списка ранее введённых имён» начиная с этапа 18).

## Решения по инфраструктуре

Приняты 24 августа 2026 года вместе с началом этапа 14.

- переход ведётся в ветке `server-edition`; `main` остаётся рабочей локальной
  версией, пока этап 16 не пройдёт приёмку;
- в проекте появляется зависимость от Node.js LTS: тесты, Supabase CLI и
  Edge Functions;
- локальный стек Supabase в Docker не используется; работа идёт против двух
  облачных проектов — `cinevault-dev` и `cinevault-prod`, миграции
  накатываются через `supabase db push`;
- ~~`cinevault-prod` переводится на платный тариф ради ежедневных копий~~ —
  пересмотрено 27 августа 2026 года: оба проекта остаются на бесплатном
  тарифе, а резервные копии снимаются своими силами (`npm run backup`) и
  восстанавливаются `npm run restore`. Путь восстановления проверяется
  сквозной проверкой `npm run check:backup`, а не обещанием;
- копия снимается через служебный ключ по API, а не `pg_dump`: Docker и
  клиент Postgres на рабочей машине не установлены. Копия покрывает данные
  и список аккаунтов, но не пароли (их не отдаёт никакое API) и не схему —
  схема живёт в миграциях;
- домен покупается свой (порядка 10 $ в год): он нужен не столько сайту,
  сколько письмам — отправитель на своём домене с SPF, DKIM и DMARC;
- регистрация закрытая, по кодам приглашений; открытая регистрация может быть
  включена позже настройкой;
- гостевого режима без аккаунта нет; для демонстрации используется отдельный
  демо-аккаунт;
- письма отправляет Resend со своего домена; шаблоны писем на русском языке;
- статика размещается на Cloudflare Pages; сборщик не используется,
  `@supabase/supabase-js` лежит в `vendor/` как ESM-файл;
- анонимный ключ Supabase хранится в `src/config.js` открыто: он публичный по
  назначению, доступ ограничивают политики RLS. Ключ `service_role` и пароль
  базы в репозиторий не попадают никогда;
- сборки для Windows удаляются: `CineVault.cmd` становится ярлыком на адрес
  сервиса, `launch.py` остаётся только dev-сервером статики.

## Рабочие решения до отдельного согласования

Эти решения приняты для продолжения разработки и могут быть изменены:

1. Пул фиксируется при старте сессии.
2. Выбывший участник не заменяется следующим элементом очереди во время
   текущего батл-рояля.
3. Очередь сдвигается при формировании следующей сессии.
4. До подтверждения выбывания разрешена перекрутка без лимита.
5. Удаление франшизы сохраняет её фильмы как самостоятельные.
6. Оценку победителю можно не ставить сразу.
7. Вложенность пользовательских списков не ограничивается моделью данных.
8. Автоматическая загрузка метаданных необязательна: карточку по-прежнему
   можно заполнить руками.
9. ~~Первая версия синхронизации — экспорт и импорт резервного файла.~~
   Синхронизация постоянная и серверная; файлов в приложении не осталось
   вовсе.
10. Франшиза занимает одну позицию в списке и очереди.
