# План: аккаунты, друзья и серверное хранение

Документ описывает переход CineVault от локального однопользовательского
приложения к онлайн-сервису с аккаунтами, друзьями и общими сессиями колеса.
Волны 7–9 (метаданные TMDB, умные подборки, импорт из внешних сервисов)
отложены до завершения этого перехода — см. последний раздел.

## Входные условия

Решено заказчиком:

- бэкенд — **Supabase** (Postgres, Auth, Realtime, Storage, Edge Functions);
- **работа без интернета больше не требуется**: клиент тонкий, источник правды
  — сервер, локально остаётся только кэш;
- вход — **email и пароль**;
- с друзьями разделяются: совместное колесо в реальном времени, просмотр
  библиотеки друга, общие списки и коллекции, общие оценки и «кто что смотрел».

## Что это ломает

Переход отменяет четыре зафиксированных решения из `DECISIONS.md`. Их нужно
переписать до начала работ, иначе документация начнёт противоречить коду:

| Было | Становится |
| --- | --- |
| обязательная работа без интернета | приложение требует сети, офлайн показывает экран «нет связи» |
| основной слой хранения — IndexedDB | основной слой — Postgres в Supabase; IndexedDB остаётся кэшем последнего снимка |
| приложение личное, обычно два зрителя | приложение многопользовательское, данные принадлежат аккаунту |
| первая версия синхронизации — экспорт и импорт файла | синхронизация постоянная, файл остаётся только резервной копией |

Кроме решений меняется способ доставки:

- **`.exe` и переносимая сборка теряют смысл.** Приложение становится
  веб-сайтом. `build-windows.ps1` и `build-portable.ps1` либо удаляются, либо
  оставляют только ярлык, открывающий адрес сервиса.
- **`launch.py` перестаёт быть частью продукта** и остаётся локальным
  dev-сервером. Его три серверные функции переезжают: TMDB-прокси — в Edge
  Function, кэш постеров — в Storage, авторезервные копии на диск — в Postgres
  и в ручной экспорт JSON.
- **TMDB-токен перестаёт быть личным файлом пользователя.** Он становится
  секретом Edge Function, одним на весь сервис. Экран «подключите свой токен»
  из настроек уходит.

## Архитектура

```
браузер
  ui/*            — без изменений
  domain/*        — чистые правила, БЕЗ изменений (ключевая ценность)
  data/gateway.js — новый слой: единственное место, знающее про Supabase
        │
        ├── supabase-js ──► Postgres + RLS      (библиотека, друзья, списки)
        ├── supabase-js ──► Realtime            (журнал событий колеса)
        ├── fetch       ──► Edge Functions      (TMDB-прокси, спин, импорт)
        └── supabase-js ──► Storage             (постеры)
```

Главное архитектурное решение: **`src/domain/*` не переписывается.** Это
чистые функции без обращений к хранилищу, и Edge Functions на Deno умеют
импортировать те же ES-модули. Правила колеса, статусы и рейтинги остаются в
одном экземпляре кода, который исполняется и в браузере, и на сервере — иначе
пришлось бы дублировать `rollEngine.js` в SQL и расходиться с ним при первой же
правке.

Второе решение: `src/data/libraryRepository.js` уже является единственным
швом между приложением и хранилищем (32 места вызова в `main.js`). Он
переписывается изнутри на Supabase, сигнатуры сохраняются. `database.js`
деградирует до кэша.

Сборки в проекте нет — только нативные ES-модули. `@supabase/supabase-js`
кладём как ESM-файл в `vendor/` и импортируем напрямую, чтобы не заводить
Vite ради одной зависимости. Если зависимостей станет больше двух — переходим
на Vite и тогда же получаем `.env` для ключей.

## Модель данных

Эскиз схемы. Все таблицы получают `owner_id uuid references auth.users`,
`created_at`, `updated_at`.

```sql
profiles(id pk → auth.users, handle citext unique, display_name,
         library_visibility text check in ('private','friends') default 'private')
user_settings(user_id pk, data jsonb)          -- нынешние DEFAULT_SETTINGS

categories(id, owner_id, parent_id, name, normalized_name, position, roll_quota)
movies(id, owner_id, category_id, category_position, title, normalized_title,
       original_title, tmdb_id, overview, genres text[], tags text[], notes,
       is_favorite, status, watched_at, cover_path, release_year,
       duration_minutes, country, tmdb_updated_at, deleted_at)
franchises(id, owner_id, category_id, category_position, name, normalized_name)
franchise_movies(franchise_id, movie_id, position)   -- вместо массива movieIds

participants(id, owner_id, name, normalized_name, last_used_at)
ratings(id, movie_id, owner_id, rater_user_id uuid null, rater_name text,
        value numeric(3,1))
  -- уникальность: (movie_id, coalesce(rater_user_id::text, normalized_name))

friendships(id, requester_id, addressee_id,
            status check in ('pending','accepted','blocked'), responded_at)
  -- уникальная пара в любом порядке

shared_lists(id, owner_id, name)
shared_list_members(list_id, user_id, role check in ('owner','editor','viewer'))
shared_list_items(list_id, movie_id, added_by, position)

roll_sessions(id, host_id, status, state jsonb, save_threshold, completed_at)
roll_session_members(session_id, user_id, saves_left, joined_at)
roll_events(id, session_id, seq bigserial, actor_id, type, payload jsonb)
```

Отличия от нынешней модели, о которых нужно помнить при переносе:

1. `franchise.movieIds` разворачивается в таблицу связей — иначе порядок
   фильмов внутри франшизы нечем защитить от одновременной правки.
2. `movie.ratings` (вложенный массив) разворачивается в таблицу `ratings` —
   иначе оценка друга требует права на запись во весь фильм.
3. Оценка перестаёт опираться только на имя: `rater_user_id` заполняется для
   зарегистрированных зрителей, `rater_name` остаётся для гостей за столом.
   Правило «одна оценка на зрителя» переезжает в уникальный индекс.
4. `createId()` иногда выдаёт `cv-<time>-<rand>` вместо UUID (запасная ветка
   без `crypto.randomUUID`). Postgres такие идентификаторы в `uuid` не примет —
   при переносе они перегенерируются, ссылки перекладываются по карте.

## Права доступа

Вся защита — на Row Level Security, клиент ходит только с анонимным ключом.
`service_role`-ключ не попадает в браузер ни при каких условиях.

Основа — одна вспомогательная функция:

```sql
create function public.is_friend(a uuid, b uuid) returns boolean
language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from friendships f
    where f.status = 'accepted'
      and ((f.requester_id = a and f.addressee_id = b)
        or (f.requester_id = b and f.addressee_id = a))
  );
$$;
```

Дальше политики читаются глазами:

```sql
create policy movies_select on movies for select using (
  owner_id = auth.uid()
  or (is_friend(auth.uid(), owner_id)
      and exists (select 1 from profiles p
                  where p.id = movies.owner_id
                    and p.library_visibility = 'friends'))
);
create policy movies_write on movies for all
  using (owner_id = auth.uid()) with check (owner_id = auth.uid());
```

Чужая библиотека таким образом доступна только на чтение и только при явно
включённой видимости. Общие списки — единственное место, где запись разрешена
не владельцу: через `shared_list_members.role`.

## Совместное колесо

Сессия становится журналом событий, а не объектом в памяти.

- `roll_events` — упорядоченный журнал (`seq`), клиенты подписаны на него
  через Realtime.
- Каждый клиент применяет к журналу **тот же чистый редьюсер из
  `rollEngine.js`**, что и сегодня. Одинаковый журнал → одинаковое состояние,
  расхождение невозможно.
- Единственное, что нельзя доверять клиенту, — случайность и право хода.
  Поэтому спин выполняет Edge Function `roll-spin`: проверяет, что вызывающий
  — ведущий сессии, берёт случайный индекс на сервере, применяет редьюсер,
  пишет событие. Клиент получает индекс и **докручивает анимацию до него** —
  визуально это то же колесо, что сейчас.
- Сейв тратит только владелец сейва (`roll_session_members.saves_left`),
  проверка — там же, в Edge Function.
- `roll_sessions.state` хранит свёрнутый снимок, чтобы присоединившийся
  посреди сессии не перечитывал весь журнал.

Побочная выгода: незавершённая сессия теперь переживает закрытие вкладки —
спорный пункт волны 6 закрывается сам собой, без отдельного решения.

## Этапы

Нумерация продолжает `ROADMAP.md`. Размер: S — день-два, M — неделя, L — больше.

### Этап 14. Фундамент Supabase (M)

- проект Supabase, локальная разработка через Supabase CLI;
- SQL-миграции: все таблицы выше, индексы, ограничения;
- RLS включён на каждой таблице, политики написаны;
- сиды с двумя тестовыми пользователями и их библиотеками;
- скрипт `npm run db:reset`, миграции в Git.

*Критерий готовности:* тест-скрипт заходит двумя пользователями и подтверждает,
что чужие строки не видны, а после `accepted`-дружбы видны на чтение.

### Этап 15. Авторизация (M)

- экран входа и регистрации, подтверждение почты, восстановление пароля;
- гейт приложения: до входа UI не рендерится;
- профиль: отображаемое имя и уникальный `handle` для поиска друзей;
- хранение сессии, тихое обновление токена, корректный выход;
- удаление аккаунта со всеми данными и экспорт своей библиотеки;
- экраны «нет сети» и «сессия истекла» вместо белого окна.

*Критерий готовности:* новый пользователь регистрируется, подтверждает почту,
входит с другого устройства и видит своё пустое хранилище.

### Этап 16. Перенос библиотеки на сервер (L)

Самый крупный и самый рискованный этап.

- `libraryRepository.js` переписан на Supabase с сохранением сигнатур;
- `commitLibraryChanges` переезжает на RPC-транзакцию (батч должен остаться
  атомарным, иначе массовые операции будут рвать связи);
- IndexedDB низведён до кэша последнего снимка для мгновенного старта;
- перенос существующей библиотеки: экспорт JSON из старой версии → «Перенести
  библиотеку» при первом входе → `parseBackup` из `domain/backup.js`,
  нормализация идентификаторов, вставка через RPC `import_library(jsonb)`;
- оптимистичная блокировка по `updated_at` и внятное сообщение при конфликте.

*Критерий готовности:* библиотека заказчика (реальный экспорт) переносится
целиком, все связи — списки, франшизы, очереди, оценки — совпадают с исходными,
и та же библиотека открывается на втором устройстве.

### Этап 17. Инфраструктура и доставка (M)

- Edge Function `tmdb` вместо прокси в `launch.py`, токен — секрет функции;
- постеры в Storage, публичные URL, удаление вместе с фильмом;
- хостинг статики и домен; переменные `SUPABASE_URL` и anon-ключ;
- судьба `launch.py`, `build-windows.ps1`, `build-portable.ps1`, `CineVault.cmd`;
- ежедневная резервная копия базы и проверенное восстановление;
- обновлённые `README.md`, `PRODUCT_SPEC.md`, `RELEASE_CHECKLIST.md`.

*Критерий готовности:* приложение открывается по адресу в интернете на чистой
машине, TMDB-поиск работает, восстановление из копии проверено на практике.

### Этап 18. Друзья (M)

- поиск по `handle`, заявка, принятие, отклонение, удаление из друзей;
- блокировка;
- настройка приватности библиотеки (`private` / `friends`);
- раздел «Друзья» и счётчик входящих заявок.

*Критерий готовности:* два аккаунта добавляются друг к другу; при видимости
`private` библиотека остаётся скрытой даже для друга — проверяется запросом
напрямую к API, а не только через интерфейс.

### Этап 19. Чужая библиотека и общие оценки (M)

- просмотр библиотеки друга в режиме чтения, с его статистикой;
- оценки друзей на карточке фильма, привязка `rater_user_id`;
- «кто что смотрел»: пересечение просмотренного, «оба хотим посмотреть»;
- существующие оценки по именам сопоставляются с аккаунтами вручную, одним
  экраном сопоставления.

*Критерий готовности:* оценка, поставленная другом, видна в обеих библиотеках и
учитывается в среднем рейтинге ровно один раз.

### Этап 20. Совместное колесо (L)

- создание сессии, приглашение друзей ссылкой или из списка;
- журнал `roll_events` + Realtime, редьюсер из `rollEngine.js`;
- Edge Function `roll-spin`: право хода, серверная случайность, сейвы;
- синхронная анимация, присоединение посреди сессии, восстановление после
  разрыва связи;
- пул из библиотек нескольких участников.

*Критерий готовности:* два браузера видят один и тот же спин, один и тот же
результат выбывания и одного победителя; закрытие вкладки ведущего не теряет
сессию.

### Этап 21. Общие списки и коллекции (L)

- совместный список с ролями (владелец, редактор, читатель);
- добавление фильмов из своей и чужой библиотеки;
- ручной порядок при одновременной правке (позиции с зазором, не целые);
- удаление участника и передача владения.

*Критерий готовности:* два пользователя одновременно правят один список без
потери чужих изменений и без дублей.

## Тесты

- `domain/*` не меняется — существующие наборы тестов остаются рабочими и
  становятся страховкой при переносе. Их нельзя ослаблять.
- Новое: тесты RLS (два клиента, проверка видимости и записи), тесты
  переноса библиотеки (эталонный JSON → база → обратный экспорт совпадает),
  тесты Edge Functions, сквозной сценарий совместной сессии на двух клиентах.
- Ручная приёмка колеса в двух браузерах остаётся в `RELEASE_CHECKLIST.md`.

## Риски

1. **Этап 16 — единственное место, где можно потерять реальную библиотеку.**
   Обязательное правило: перенос только копированием, старая локальная база
   не трогается, пока перенос не подтверждён экспортом-сверкой.
2. **Пауза бесплатного тарифа.** По текущим правилам Supabase бесплатный
   проект засыпает после недели без обращений, и первый запрос после этого
   упирается в пробуждение. Для приложения, которым пользуются раз в две
   недели, это заметно — либо платный тариф, либо пинг по расписанию.
3. **Приложение начинает хранить чужие данные.** Удаление аккаунта со всеми
   данными и экспорт своей библиотеки нужны не «потом», а в этапе 15.
4. **Общие списки (этап 21) — самая дорогая часть** и единственная, где два
   человека пишут в одну запись. Если сроки поджимают, режется первой:
   совместное колесо и чужие библиотеки ценность дают и без неё.
5. **Потеря офлайна необратима для сценария «ноутбук на даче».** Если такой
   сценарий всё-таки существует, лучше узнать это сейчас, а не после этапа 16.

## Открытые вопросы

- домен и почтовый отправитель для писем подтверждения (без своего домена
  письма Supabase уходят в спам);
- один общий TMDB-токен на сервис или каждый пользователь приносит свой;
- сколько людей ожидается — от этого зависит тариф;
- нужен ли гостевой режим без регистрации (сейчас в плане его нет);
- что делать с `.exe`: удалить или оставить ярлык на веб-версию;
- сохраняется ли требование «интерфейс только на русском» для писем и ошибок
  Supabase (они по умолчанию английские, нужен свой шаблон).

## Волны 7–9

Отложены целиком. Что с ними станет после перехода:

- **Волна 7 (режиссёры, актёры, автоколлекции, трейлеры, обновление карточек).**
  Не дешевеет и не дорожает, но делать её до этапа 16 — значит переносить
  вдвое больше полей. Ждёт.
- **Волна 8 (умные подборки, подбор под время, «где смотреть», цель года).**
  Дешевеет: сохранённые фильтры и цели естественно ложатся в `user_settings`,
  а подборки становятся общими с друзьями почти бесплатно.
- **Волна 9 (импорт из Кинопоиска и IMDb, слияние дублей, кэш постеров,
  горячие клавиши).** Поиск дублей переезжает на сервер и становится проще;
  управление кэшем постеров теряет смысл (Storage, этап 17); горячие клавиши
  ни от чего не зависят и могут быть сделаны в любой момент как передышка.
